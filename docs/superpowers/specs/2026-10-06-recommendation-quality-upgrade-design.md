# 无后端个性化推荐质量升级方案

- 日期：2026-10-06
- 状态：提案，尚未实施；本轮只编写本文档。
- 依据：当前工作区源码（包含未提交改动）、本地受控实验、已有设计与公开资料。
- 核心目标：减少连续多首不合口味，让陌生歌曲也更贴近用户真实喜好，而不是要求用户额外标注或“训练算法”。

## 1. 结论与推荐路线

还有明显优化空间，但下一步不宜继续堆叠权重或随意安装推荐库。

当前实现已经有会话纠偏、中文分词、歌单共现、会话共现、动态通道配额、长期歌手偏好，以及端侧音频模型。问题是部分能力没有可靠地作用于实际待播歌曲，音频信息也没有直接用于判断陌生单曲是否合口味。

建议采用以下顺序：

> 修通实际选歌与纠偏链路 → 校验音频模型确实有效 → 单曲音频理解与多口味画像 → 扩展相关候选并统一排序 → 根据实测决定是否引入更强模型或外部相似曲数据。

推荐主线是“现有引擎 + 小型端侧音乐模型 + 本地多兴趣排序”，不另造服务器，不推倒现有播放器。

### 三条路线比较

| 路线 | 主要变化 | 优点 | 局限 | 建议 |
| --- | --- | --- | --- | --- |
| A. 修链路、收紧选歌 | 修待播纠偏、排序前筛选、限制低置信度探索 | 改动相对小，直接针对连续踩雷 | 对陌生歌曲的理解仍有限 | 必做的第一阶段 |
| B. A + 端侧内容理解 | 真正的歌曲特征向量、多兴趣画像、候选预分析、本地融合排序 | 不依赖额外服务，有机会改善陌生歌匹配 | 需要验证音频预处理、耗电、流量与模型许可 | 推荐主线，分阶段推进 |
| C. B + 外部相似曲数据 | 公共服务或许可允许的静态数据提供歌曲邻居 | 可补足“别人也喜欢这些歌”的关联信息 | 覆盖、隐私、服务稳定性和授权有额外限制 | 可选增强，不作为核心依赖 |

不能承诺达到所有主流平台的整体推荐水平：平台还拥有大规模用户行为、完整曲库特征、长期实验数据和内容运营。无后端方案可以争取在用户熟悉的口味区域与连续收听体验上明显靠近，但没有可信依据给出“达到平台多少百分比”。

## 2. 约束与非目标

### 默认约束

1. 推荐计算、个人画像、播放反馈保留在设备本地。
2. 继续使用现有音乐源获取歌曲与歌单；“无后端”不等于完全断网。
3. 主线不增加第三方画像上传、云端推理或必须注册的账号。
4. 不要求新增评分问卷、标签选择流程或频繁点击反馈；利用现有收藏、歌单与自然播放行为。
5. 复用现有推荐入口、播放器和设置，不重复增加界面。
6. 保持固定竖屏，不修改屏幕方向约定。
7. 不清空已有画像或历史，不以重新冷启动掩盖问题。
8. 不改变现有“在库歌曲不作为外部推荐候选”的规则；救场曲也应优先从与偏好强相关的陌生歌中选择，不擅自改成收藏回放。

### 本方案不做

- 不引入需要自建服务的推荐平台或在线向量数据库。
- 不把通用大语言模型当作“懂用户品味”的替代品。
- 不因为某个库名称带“协同过滤”就认为单机自动拥有海量用户数据。
- 不批量抓取整个曲库、不绕过来源服务限制、不依赖未经许可的音频下载。
- 不默认下载大型模型或持续在后台分析整首音频。

## 3. 当前实现中最重要的问题

以下区分源码事实、受控实验和仍待真机验证的结论；没有把旧设计文档的“已实现”直接当作有效性证明。

### 3.1 连续跳歌的纠偏没有覆盖实际待播列表

**已确认的代码事实：**

- `src/core/recommend/radio.ts:173` 首次获取20首，存入独立的 `pending`。
- `src/core/recommend/index.ts:519` 通过 `queue.shift` 把歌曲从引擎队列取走。
- `src/core/recommend/index.ts:747` 的安全模式只遍历引擎内部队列。
- `src/core/recommend/radio.ts:152` 虽然监听撤队通知，但安全模式没有检查已移交的歌曲，也就不能可靠地为它们产生撤队通知。

使用项目实际 `createRadioQueue` 函数做了受控实验：20首全部移交后，`pending` 有20首，安全模式可见的内部队列有0首。

**影响：** 系统可能已经发现用户在连续切歌，但下一首仍然从之前排好的列表里取出。继续提高负反馈权重，不能替代这个链路修复。

**边界：** 该实验确认了队列可见性缺口，不代表已经复现用户真机每次连续失配的完整过程。

### 3.2 现有音频模型不能视为已经可靠生效

**已确认的代码事实：**

- `android/app/src/main/java/cn/toside/music/mobile/audioFeature/TfliteModule.java:83` 的 `@ReactMethod` 使用 `float[]` 接收输入。
- 当前 React Native 桥接参数解析支持 `ReadableArray`，不支持这个数组类型；见 `node_modules/react-native/ReactAndroid/src/main/java/com/facebook/react/bridge/JavaMethodWrapper.java:279`。
- 模型文件已存在，但输出是 `model/Sigmoid` 的50维标签分数，不是为细粒度相似性选取的中间层表征。
- 模型标识写死为 `musiconn-discogs`，见 `src/core/recommend/audioFeature.ts:110`；文件名称不能证明实际模型训练来源或版本。

**判断：** 原生编译通过、模型文件在包内、张量维度正确，都不足以证明真实歌曲分析成功或输出可用于相似度排序。

**待验证：** 当前安装包是否与源码一致、真机桥接报错方式、成功分析数量，以及预处理与参考实现的一致性。

### 3.3 音频信息覆盖小，且间接作用于整个歌单

当前流程只在电台歌曲自然播放结束后安排分析，见 `src/core/recommend/index.ts:725`；不会先分析候选歌曲，也没有优先分析已有收藏种子的流程。

限制包括：

- 每5分钟最多启动一次、每日最多20次成功分析，见 `src/core/recommend/config.ts:84`。
- 某歌单被分析的歌曲不足已获取歌曲的30%，就完全不给音频分，见 `src/core/recommend/audioEmbedding.ts:103`。例如已获取50首时，需要至少15首已分析。
- 当前将非排除歌曲平均为一个口味中心，见 `src/core/recommend/audioEmbedding.ts:69`。
- 音频分只占A通道原始分的10%，并以来源歌单为单位加分，见 `src/core/recommend/candidatePool.ts:221`。

**影响：** 即使管线跑通，陌生候选仍可能没有音频证据；同歌单的一首合口味，也不能证明剩余歌曲都合口味。只调整这个10%的系数不能解决覆盖与归因问题。

### 3.4 当前抽样容易让大量低分候选压过少量高分候选

`src/core/recommend/candidatePool.ts:259` 把通道分限制在0.01～1；`src/core/recommend/diversity.ts:6` 对合格候选进行指数概率抽样，默认温度为0.6。

使用项目实际抽样函数、均匀覆盖随机输入的受控实验：

| 合成候选集合 | 温度 | 选中唯一高分候选的比例 |
| --- | --- | --- |
| 1首分数0.8，10首分数0.2 | 0.6 | 21.37% |
| 同上 | 0.35（当前安全模式） | 35.70% |

这不是用户实际命中率，也不说明分数0.8必然好听；它说明当前选择机制即使面对明显分差，仍可能大量选中低分歌曲。

**调整重点：** 先筛选质量，再在合格候选里做适量随机；不是只把温度改小，更不是直接把未经校准的分数当喜欢概率。

### 3.5 已有学习组件不等于获得新的音乐理解

- 歌名分词可以识别“Live、DJ、伴奏”等版本信息，但“夜晚、告别”等普通标题词不可靠地代表音乐风格。当前词面反馈可能把这些词也用于偏好与召回，见 `src/core/recommend/tokenFeedback.ts:18`、`:66`。
- 当前会话共现主要给历史中出现过的歌曲加分，见 `src/core/recommend/similarity.ts:213`；它不能自动为从没听过的新候选生成关系。
- 最近7天电台歌曲又会被候选过滤，见 `src/core/recommend/filter.ts:56`。这不表示会话共现完全无效，但必须测量它在实际陌生候选中的非零覆盖，而不是仅看函数单测通过。
- 歌手和来源歌单有用，但同一歌手、同一大歌单中可能有多种风格。只按歌手或整个分类降权，容易误伤用户其实喜欢的方向。

## 4. 推荐的目标流程

```text
现有收藏、歌单、真实播放反馈
              ↓
本地多口味画像 + 当前会话意图
              ↓
多路相关候选：歌单关系、种子近邻、歌手邻域、适量探索
              ↓
低成本筛选与可播放性判断
              ↓
预算内为靠前候选补充音频特征
              ↓
统一的单曲级相关性排序
              ↓
质量底线 + 多样性约束 + 少量随机
              ↓
即将播放的短队列
              ↑
喜欢／跳过／不感兴趣后重新评估尚未播放的推荐曲
```

候选池可以大，缓存可以提前准备，但不应把长期预取的歌曲顺序当成不可更新的播放决定。

### 4.1 第一优先级：让纠偏真正影响下一首

- 明确引擎队列、`pending`、播放器已提交补位曲的归属与版本。
- 对全部“尚未播放且属于电台”的歌曲进行重评分或撤换，而不是只扫描一个内部队列。
- 不动正在播放的歌曲，不删除用户手动加入的“稍后播放”，不破坏上一首历史。
- 初始以1～2首为短提交窗口；这个数字是实验起点，不是质量承诺。
- 普通跳过更新会话偏好；连续负反馈再触发更强的方向切换。
- 同时处理异步竞争：已经触发的下一首切换可能早于反馈结算完成。明确取消、重选与不能追溯修改的边界，避免宣称所有反馈都能瞬时改变已经开始播放的歌曲。
- 旧版本预取结果不能在重排完成后重新塞回旧候选。

负反馈的归因范围由证据决定：单首被跳过，不直接否定整位歌手或整个“华语”分类；多首同一细分方向持续负反馈，再加强该方向的临时降权。

### 4.2 第二优先级：从“猜歌单”转成“比较歌曲本身”

先修通现有 TFLite 管线，再评估模型更换。

必须建立一组固定音频样本，比较参考实现与手机端的预处理及模型输出：相同音频应得到接近的结果，不同风格应有可解释的区分。随机输入能跑通、向量余弦接近1等内部测试不能替代这一步。

音频表征需要两种输入：

1. **偏好锚点：** 从现有收藏、歌单中按不同口味选代表歌曲，不只等推荐曲自然播完后慢慢积累。
2. **待选歌曲：** 对粗排靠前、缺少特征的少量候选预分析，直接计算“这首歌像不像用户喜欢的歌”。

执行原则：

- 优先复用合法可访问的本地文件或现有缓存，不假设所有播放源都支持任意片段读取。
- 初始按少量短片段评估；是否需要多片段，由效果与成本决定，避免只分析片头造成偏差。
- 按时间、流量、CPU和设备状态控制任务预算；失败也消耗预算，避免源异常时反复请求。
- 不要求分析整个候选池；没有音频特征表示“未知”，不是“不喜欢”。
- 现有每日20次预算需要重新测量后配置，不能一边新增候选预分析，一边假设旧预算足够。
- 特征缓存绑定实际模型版本、输出层、预处理版本与歌曲版本；更换模型后不能混用旧向量。
- 稀疏音频证据按置信度温和参与融合，不再依赖整张歌单达到30%覆盖才开始发挥作用。

### 4.3 第三优先级：同时保留多种口味

一个人可以喜欢安静女声，也可以喜欢摇滚；把两者平均成一个中心，可能得到既不安静也不够摇滚的中间结果。

建议：

- 根据已有正反馈歌曲维护少量兴趣中心；样本不足时不强行分组。
- 收藏、反复主动播放的证据强于单次后台播完；不把所有已分析歌曲等权处理。
- 候选分别与各兴趣中心比较，再结合最近几首的反应决定当前更靠近哪个方向。
- 连续跳过时临时切换方向，而不是立即改写长期口味。
- 明确不感兴趣的歌曲维持已有屏蔽语义；相似内容的软降权不自动变成永久屏蔽。

分组数量与权重以本地样本量和实验结果决定，不预先写死成固定四类，也不需要用户手动选择。

### 4.4 第四优先级：提高候选质量，而不只是扩大候选数量

“从500首扩大到5000首”只有在新增歌曲与用户有关时才有意义。

优先复用现有歌单观察与共现索引，增强为可解释的歌曲邻居关系：

- 一首陌生歌若多次出现在包含用户喜欢歌曲的不同歌单中，获得关联证据。
- 对超大杂烩歌单、热门歌曲和高度重复的歌单做降权，避免它们天然占优。
- 区分某歌手最热门的歌与真正靠近用户偏好歌曲的作品。
- 风格、语言、年代、版本等信息只有在来源可靠时才作为约束；普通歌名词不充当风格标签。
- 召回阶段保留来源差异，最终排序阶段优先比较歌曲质量，不为了填满通道配额硬塞低相关候选。
- 本地会话共现只作为辅助，统计它真正覆盖了多少新候选；不能以“移植了SAR”替代效果评估。

在获得可靠单曲特征后，可以进一步利用本地已分析歌曲的近邻关系扩展候选。但只有几百至几千个向量时，直接计算相似度通常足以作为起点，不先引入大型向量数据库。

### 4.5 第五优先级：统一排序、受控探索

把当前大量分散加权收敛为可测量的融合排序：

- 单曲音频与各兴趣中心的相似度。
- 与收藏种子的歌单关联证据。
- 当前会话方向、长期歌手偏好。
- 版本偏好、最近负反馈、重复与来源集中度。
- 证据完整度、来源可靠性与新颖度。

先使用可解释、可回放验证的融合分数；有足够有效播放记录后，再评估小型本地线性／逻辑回归排序器是否优于固定权重。不能拿少量带偏差的播放样本直接训练复杂模型。

选择策略：

1. 屏蔽明确禁用项，剔除已确认不可播放项。
2. 对候选相关性排序，保留当前批次中相对可靠的一部分。
3. 在可靠候选中打散歌手、作品、来源和风格，再做低强度随机。
4. 个性电台以贴合为主；探索未知保留更高探索比例，但探索也应围绕可解释的邻近方向。
5. 个性电台可用“约85%～90%相关候选、10%～15%邻近探索”作为首轮对照起点；需要按覆盖率和实际负反馈调整，不作为固定产品承诺。
6. 连续负反馈时暂缓低置信度探索，避免为了完成配额继续冒险；恢复后逐步放开。

所有通道分数必须校准或统一计算后才能横向比较，不直接设置一个任意的“0.7以上必喜欢”门槛。

## 5. 外部项目与组件选择

### 5.1 首选：复用现有 TFLite 与 MusiCNN，再比较真实表征

**作用：** 不看歌名也能从音色、节奏、配器等声音信息中提取相似性线索。

**引入方式：** 复用已存在的原生解码与推理框架，先保证桥接、预处理、模型版本正确；对比当前50维标签输出与适合相似性任务的中间层表征。

**为什么不直接换运行时：** 当前首要缺口是桥接与模型接法，不是证明了 TFLite 不够好。更换运行时本身不会增加推荐质量。

**验收前提：** 参考输出一致性、真实歌曲区分度、Android真机延迟／内存／耗电、模型权重分发许可。

### 5.2 候选升级：Essentia / MTG 的 Discogs-EffNet 等音乐表征

**作用：** 作为比当前粗粒度标签头更适合歌曲相似性比较的候选方案。

**引入方式：** 先在固定歌曲样本上与现有模型对照；确认对目标曲库有收益，再验证转换格式、算子支持、量化损失和移动端成本。

**重要边界：** 这是待评估候选，不是已经证明可直接替换的 TFLite 文件，也不保证对华语音乐或个人喜好一定更好。维度更高不等于推荐更准。

### 5.3 不作为首发默认：MERT 等更大音乐模型

MERT可以作为音乐表征的对照候选，但模型规模、运行内存和推理成本与当前小模型不同。首轮更适合在开发环境比较其“相似歌判断”是否确实更好，而不是直接把大模型塞进安装包。

只有在目标曲库效果明显改善、端侧成本可接受且权重授权明确时，才考虑量化后的端侧版本。开发机离线评测不等于应用运行需要服务器。

### 5.4 可选数据增强：Last.fm 相似曲

Last.fm 的 `track.getSimilar` 官方说明是基于收听数据返回相似歌曲，可为设备提供已有的歌曲关联，而不是要求本应用自建用户行为后台。

但应明确：

- 它是第三方服务，不是本地开源组件；如果“无后端”要求连额外第三方服务也不能用，就不采用。
- 不需要上传完整播放历史，但查询具体种子歌曲本身仍可能暴露部分偏好，接入前需要明确同意。
- 需要 API key，歌曲名／歌手名与现有音源的匹配会失败；华语、冷门曲覆盖必须抽样验证。
- 遵守商用授权、署名、缓存与请求限制；不能把服务返回内容当作无限制可分发的数据集。
- 返回结果只能作为候选关联证据，仍须本地排序；不能因为服务返回“相似”就直接播放。
- 服务不可用时保留完整的本地推荐能力，不阻塞播放。

因此列为第三阶段之后的可选增强，而不是本次主线。

### 5.5 辅助身份数据：MusicBrainz

更适合补充歌曲／艺人身份、版本与元数据，不是直接的个人推荐引擎。

只有在确认跨源同名、不同版本误匹配是明显瓶颈后才评估接入；同样需要验证目标曲库覆盖、请求限制和数据使用条件。不能指望仅添加 MusicBrainz 就获得平台级推荐。

### 5.6 授权与资料核验说明

- 开源推理代码、预训练权重、训练数据、第三方返回数据是不同的授权对象。
- 仅加载模型文件不等于自动取得任意商业分发权，也不能据此断言没有任何许可证义务。
- 本轮检索找到了官方模型页与使用文档，但 Essentia、部分 Hugging Face 页面在当前环境访问失败；具体模型许可、转换兼容性和移动性能必须在选择具体文件时重新核验。
- 默认不引入授权不清晰、必须提交用户画像或必须运行自建服务的组件。

## 6. 分阶段实施与退出条件

### 阶段一：纠偏与效果可观测性

范围：修待播列表纠偏盲区、异步版本问题和选歌前质量筛选；记录本地推荐来源、关键分项、模型状态与反馈生效时点。

通过条件：

- 连续负反馈可以影响尚未播放的实际电台队列，不只改变引擎内部数字。
- 用户手动稍后播放、上一首和自然续播不受破坏。
- 能区分普通跳过、明确不喜欢、播放失败和应用退出，不把网络失败当口味负反馈。
- 诊断数据留在本地，开发日志不上传、不包含音频直链或凭据。

### 阶段二：验证音频能力，建立单曲级比较

范围：修桥接、用固定音频对齐参考实现、建立模型版本缓存、分析现有偏好锚点和少量候选。

通过条件：

- 真机有实际分析成功记录，而不只是模型文件存在。
- 音频特征能区分固定样本，且与参考实现一致。
- 明确知道候选特征覆盖率、失败率与每分钟收听增加的分析成本。
- 播放启动、稳定性与设备温度不因后台任务明显恶化。

### 阶段三：多口味画像与相关候选融合

范围：将单中心改为样本量支持的多兴趣表示；增强现有共现邻居，统一单曲排序，调整探索策略。

通过条件：

- 不因一种口味的负反馈永久压制另一种口味。
- 相比阶段一基线，陌生歌早切与连续早切下降，且不是靠重复熟悉歌曲实现。
- 新歌手发现、收藏或完整收听等指标没有明显退化。

### 阶段四：按数据决定外部增强

范围：在统一测试样本上比较现有模型、中间层表征和更强音乐模型；如果本地召回仍明显缺乏关联数据，再单独决定是否接入外部相似曲服务。

通过条件：外部能力带来的收益超过其耗电、体积、流量、授权与维护成本；没有明确收益就不引入。

每阶段独立比较基线，避免一次修改所有模块后无法知道哪些真正有效。未通过前一阶段的证据闸门，不靠叠加更多组件跳过问题。

## 7. 如何证明“更贴合”，而不只证明代码能运行

### 7.1 自动化正确性

重点覆盖：

- 首批20首移交后触发连续负反馈，实际待播项仍可撤换。
- 反馈结算、队列补位与正在进行的下一首切换交错。
- 重排后旧异步结果返回，不污染新队列。
- 用户手动队列与电台队列隔离，上一首历史保持正确。
- 音频缺失、解码失败、模型版本变化、部分候选无特征。
- 多口味不被单一均值吞并，短期跳过与长期偏好分开。
- 低分候选数量增加时，不能无限稀释质量筛选的作用。

### 7.2 真机效果验证

记录以下指标，默认只在设备本地汇总：

| 指标 | 解释 |
| --- | --- |
| 连续3首主动早切事件率 | 直接衡量连续不合口味的体验；按可比较的播放窗口统计 |
| 单首早切率 | 区分主动切歌与播放错误，并使用有效收听时长而非拖动后的进度 |
| 明确不感兴趣率 | 观察强负反馈是否下降 |
| 收藏／加入歌单率 | 观察是否更容易发现值得留下的新歌 |
| 完整收听率 | 辅助指标，不能单独等同于喜欢，后台播放可能有噪声 |
| 陌生歌曲和歌手覆盖 | 防止靠只播熟悉内容制造好看的指标 |
| 音频特征有效覆盖率 | 不只统计分析过多少首，而是统计实际候选和实际选中歌曲的覆盖 |
| 反馈到队列变化的延迟 | 区分算法更新成功与用户下一首真正受影响 |
| 启播时间、流量、耗电、错误率 | 保证质量改善没有换来不可接受的使用成本 |

验证方法：

- 保存现状基线，再逐项加入改动；不是只拿更新后的几首歌作结论。
- 按会话或交替时段比较，记录样本数、曲库和来源可用性，避免把时间差当算法收益。
- 使用过去数据做回放时按时间切分，不能把将来的收藏结果提前放进画像。
- 未曝光的歌没有真实用户标签，不能全部当“不喜欢”；历史回放也不能证明没播过的新歌会被喜欢。
- 小规模真机自然收听仍是最终依据，不要求用户额外提供大量标注。

首轮产品目标可设为“连续3首早切事件率相对基线下降约25%，同时收藏／完播、陌生歌覆盖和播放性能不明显退化”。这是待验证的目标，不是预测；样本不足、来源不稳定或统计波动大时，不宣称已达标。

## 8. 预期收益与剩余边界

最可能先看到的收益，是连续切歌后系统及时换方向，以及低分候选不再靠数量压过高分候选。

进一步的收益来自对陌生单曲的声音理解和多口味表示，而不是更多歌名关键词或更复杂的手写乘数。

即使声音很相似，用户仍可能不喜欢某首歌的歌词、人声表达或文化语境；音频相似度只是证据之一。小型端侧模型不能补齐主流平台全部的群体行为与内容知识，因此必须保留歌单关联、个人行为、来源可靠性与适量探索的融合。

## 9. 主要关联模块

| 模块 | 设计涉及范围 |
| --- | --- |
| `src/core/recommend/radio.ts` | 实际待播列表、提交窗口、用户手动队列保护 |

| `src/core/recommend/profile.ts` | 多兴趣画像与证据权重 |
| `src/core/recommend/audioFeature.ts`、`audioEmbedding.ts` | 分析调度、特征缓存、多兴趣与单曲相似度 |
| `src/core/recommend/melSpectrogram.ts`、`nativeAudio.ts` | 预处理一致性与原生桥接 |
| `android/app/src/main/java/cn/toside/music/mobile/audioFeature/` | 解码与推理运行时正确性 |
